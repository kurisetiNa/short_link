# 短链接分组代码结构解析

## 1. 整体结构

短链接分组位于 `admin` 服务，核心代码结构如下：

```text
admin/src/main/java/com/nageoffer/shortlink/admin
├─ controller
│  └─ GroupController.java
├─ dto
│  ├─ req
│  │  ├─ ShortLinkGroupSaveReqDTO.java
│  │  ├─ ShortLinkGroupUpdateReqDTO.java
│  │  └─ ShortLinkGroupSortReqDTO.java
│  └─ resp
│     └─ ShortLinkGroupRespDTO.java
├─ service
│  ├─ GroupService.java
│  └─ impl
│     └─ GroupServiceImpl.java
├─ dao
│  ├─ entity
│  │  └─ GroupDO.java
│  └─ mapper
│     └─ GroupMapper.java
├─ toolkit
│  └─ RandomGenerator.java
└─ common/biz/user
   ├─ UserInfoDTO.java
   ├─ UserTransmitFilter.java
   └─ UserContext.java
```

各层职责：

```text
Controller  接收分组 HTTP 请求并返回统一响应
ReqDTO      承接新增、修改和排序参数
RespDTO     规定查询分组返回的字段
Service     组织分组业务规则
Mapper      访问 t_group 数据库表
GroupDO     承接数据库分组记录
Toolkit     生成分组业务 ID
biz.user    提供当前登录用户上下文
```

## 2. 一次查询请求的完整链路

```text
前端 / Apifox
    ↓ GET /listGroup，Header 携带 username + token
UserTransmitFilter
    ↓ 从 Redis 查询 login_{username}[token]
UserInfoDTO
    ↓ 反序列化用户 JSON
UserContext
    ↓ 把用户信息保存到当前请求线程
GroupController
    ↓ 调用 listGroup()
GroupServiceImpl
    ↓ 取得当前 username，构造查询条件
GroupMapper
    ↓ MyBatis-Plus 生成 SQL
MySQL t_group
    ↓ 返回当前用户的 GroupDO 列表
BeanUtil.copyToList
    ↓ DO 转换为 ShortLinkGroupRespDTO
Results.success(...)
    ↓ 包装 Result<List<ShortLinkGroupRespDTO>>
前端 / Apifox
```

接口不需要传入 `username` 业务参数，因为当前用户身份已经由 Header、Redis 和 `UserContext` 传递到 Service。

## 3. GroupController：接口入口

`GroupController` 使用 `@RestController` 注册为 Spring MVC Controller，通过 `@RequiredArgsConstructor` 进行构造器依赖注入：

```java
@RestController
@RequiredArgsConstructor
public class GroupController {
    private final GroupService groupService;
}
```

五个接口的主要职责：

```java
save(requestParam)        // 接收 name，新增分组
listGroup()               // 查询当前用户分组
updateGroup(requestParam) // 接收 gid + name，修改名称
deleteGroup(gid)          // 接收 Query gid，逻辑删除
sortGroup(requestParam)   // 接收 gid + sortOrder 列表
```

Controller 只负责参数接收、Service 调用和统一响应，不直接操作数据库。

## 4. DTO：分组数据传输对象

### 4.1 ShortLinkGroupSaveReqDTO

新增分组只需分组名称：

```java
public class ShortLinkGroupSaveReqDTO {
    private String name;
}
```

### 4.2 ShortLinkGroupUpdateReqDTO

修改时需要分组标识和新名称：

```java
public class ShortLinkGroupUpdateReqDTO {
    private String name;
    private String gid;
}
```

### 4.3 ShortLinkGroupSortReqDTO

每个排序项指定一个分组的排序值：

```java
public class ShortLinkGroupSortReqDTO {
    private String gid;
    private Integer sortOrder;
}
```

Controller 接收的是 `List<ShortLinkGroupSortReqDTO>`，所以请求体应为 JSON 数组。

### 4.4 ShortLinkGroupRespDTO

查询分组时返回：

```java
public class ShortLinkGroupRespDTO {
    private String gid;
    private String name;
    private String username;
    private Integer sortOrder;
}
```

Service 使用 Hutool `BeanUtil.copyToList()` 将 `List<GroupDO>` 复制为返回 DTO 列表。

## 5. GroupService：业务能力接口

```java
public interface GroupService extends IService<GroupDO> {
    void saveGroup(String groupName);
    List<ShortLinkGroupRespDTO> listGroup();
    void updateGroup(ShortLinkGroupUpdateReqDTO requestParam);
    void deleteGroup(String gid);
    void sortGroup(List<ShortLinkGroupSortReqDTO> requestParam);
}
```

`GroupService` 声明“分组模块可以做什么”，`GroupServiceImpl` 负责“具体怎么做”。

它继承 `IService<GroupDO>`，因此还能使用 MyBatis-Plus 提供的通用 Service 能力。

## 6. GroupServiceImpl：核心业务实现

### 6.1 类的继承与注入关系

```java
@Service
public class GroupServiceImpl
        extends ServiceImpl<GroupMapper, GroupDO>
        implements GroupService {
}
```

`ServiceImpl<GroupMapper, GroupDO>` 会提供 `baseMapper`，因此实现类可以直接调用：

```java
baseMapper.insert(groupDO);
baseMapper.selectList(queryWrapper);
baseMapper.update(groupDO, updateWrapper);
```

### 6.2 新增分组

```text
生成随机 gid
    ↓
hasGid() 查询当前用户下是否可用
    ↓ 重复则继续生成
从 UserContext 获取 username
    ↓
构造 GroupDO，sortOrder = 0
    ↓
baseMapper.insert()
```

### 6.3 查询分组

查询条件包含：

- 只查询 `del_flag = 0` 的有效数据。
- 只查询 `username = 当前用户名` 的数据。
- 按 `sortOrder`、`updateTime` 倒序排列。

这个 `username` 条件实现了不同用户之间的分组隔离。

### 6.4 修改和删除

修改和删除都先获取当前用户名，并且在 SQL 条件中限定：

```text
username = 当前用户
gid = 请求中的分组标识
del_flag = 0
```

更新条数为 0 时抛出：

```java
throw new ClientException("分组不存在或无权修改");
```

删除实际执行：

```java
groupDO.setDelFlag(1);
```

因此属于逻辑删除。

### 6.5 排序

`sortGroup()` 遍历请求数组，对每个 `gid` 执行一次更新：

```text
List<SortReqDTO>
    ↓ forEach
构造只包含 sortOrder 的 GroupDO
    ↓
按 username + gid + delFlag 更新
```

## 7. GroupDO：数据库实体

```java
@TableName("t_group")
public class GroupDO extends BaseDO {
    private Long id;
    private String gid;
    private String name;
    private String username;
    private Integer sortOrder;
}
```

`@TableName("t_group")` 指定对应数据库表。`id` 使用自增策略：

```java
@TableId(type = IdType.AUTO)
private Long id;
```

`GroupDO` 继承 `BaseDO`，因此还具有：

```text
createTime
updateTime
delFlag
```

`MyMetaObjectHandler` 在插入时自动填充创建时间、修改时间和删除标识，在更新时自动填充修改时间。

## 8. GroupMapper：数据访问层

```java
@Mapper
public interface GroupMapper extends BaseMapper<GroupDO> {
}
```

Mapper 没有自定义 SQL，当前的增删改查均由 MyBatis-Plus `BaseMapper` 提供。

`LambdaQueryWrapper` 和 `LambdaUpdateWrapper` 使用 Java 方法引用指定字段：

```java
.eq(GroupDO::getUsername, username)
.eq(GroupDO::getGid, gid)
```

这种写法比直接手写字段名字符串更容易在编译阶段发现错误。

## 9. RandomGenerator：分组 ID 生成器

`RandomGenerator` 使用 `SecureRandom` 生成由数字、大写字母和小写字母组成的 6 位字符串：

```text
0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz
```

例如：

```text
a3FgP9
```

`gid` 是对外使用的业务标识，`id` 是数据库内部的自增主键，两者职责不同。

## 10. common.biz.user：当前用户基础能力

### 10.1 UserTransmitFilter

过滤器从每次请求的 Header 读取：

```java
String username = httpServletRequest.getHeader("username");
String token = httpServletRequest.getHeader("token");
```

然后查询 Redis Hash：

```text
Key: login_{username}
Field: token
Value: 用户信息 JSON
```

查询成功后，将 JSON 转换为 `UserInfoDTO` 并写入 `UserContext`。

### 10.2 UserContext

`UserContext` 使用 `TransmittableThreadLocal<UserInfoDTO>` 保存当前请求的用户，对外提供：

```java
getUserId()
getUsername()
getRealName()
```

请求处理结束后，过滤器在 `finally` 中调用：

```java
UserContext.removeUser();
```

这一步用来防止 Web 服务器复用线程时出现用户信息串号。

### 10.3 UserInfoDTO

`UserInfoDTO` 规定登录用户信息在 Java 中的形式。它有两个用途：

- 承接 Redis 中用户 JSON 反序列化后的数据。
- 作为 `UserContext` 中保存的用户对象。

三个类的关系可以记为：

```text
UserInfoDTO          用户信息长什么样
UserTransmitFilter  从 Redis 恢复用户信息
UserContext         保存并提供本次请求的用户信息
```

## 11. 多用户登录时如何查询

假设客户端同时保存：

```text
zhangsan + token-A
lisi     + token-B
```

查询张三的分组时：

```http
username: zhangsan
token: token-A
```

查询李四的分组时：

```http
username: lisi
token: token-B
```

客户端选择哪一组 Header，服务端就从 Redis 恢复哪个用户，并在 SQL 中使用该用户的 `username`。

```text
业务参数：决定查什么、改什么
认证 Header：决定为谁查、为谁改
```

## 12. 统一响应和异常

Controller 通过 `Results.success()` 返回统一结果：

```java
return Results.success();
return Results.success(groupService.listGroup());
```

修改或删除的目标不存在时，Service 抛出 `ClientException`，再由 `GlobalExceptionHandler` 转换成统一错误响应。

## 13. 代码设计中的注意点

### 13.1 无效 Token 尚未统一拦截

`UserTransmitFilter` 在 Redis 查询失败时只是不设置用户上下文，仍会继续执行 Controller。`saveGroup()` 和 `listGroup()` 也没有显式的未登录校验。

### 13.2 gid 唯一性

`hasGid()` 通过查询避免随机 ID 重复，但并发请求仍可能在查询后同时插入。数据库应增加唯一索引作为最终保障。

### 13.3 权限隔离

修改、删除和排序的 SQL 都包含 `username` 条件，这是防止跨用户操作的关键。后续新增“按分组查短链接”时也应保留相同的用户归属校验。

### 13.4 缺少数据库脚本

当前代码已将 `GroupDO` 映射到 `t_group`，但 `sql` 目录中尚未找到对应建表脚本。在新环境启动项目前需要补齐。

## 14. 分层记忆总结

```text
前端 / Apifox：传递业务参数和登录 Header
UserTransmitFilter：从 Redis 恢复当前用户
UserContext：在本次请求内提供当前用户
GroupController：接收分组请求
ReqDTO：承接分组请求参数
GroupServiceImpl：处理分组业务
GroupMapper：操作 t_group
GroupDO：承接分组数据库记录
RespDTO：承接查询返回数据
Result / Results：统一包装响应
```

最简请求链路：

```text
Header → Filter → UserContext
                        ↓
请求 → Controller → Service → Mapper → t_group
响应 ← Result 包装 ← RespDTO ← Service ← 查询结果
```
