# 短链接管理代码结构解析

## 1. 整体结构

短链接管理的核心业务位于 `project` 服务，`admin` 服务负责向后台提供接口并远程调用 `project`。

```text
shortlink
├─ admin
│  └─ src/main/java/com/nageoffer/shortlink/admin
│     ├─ controller
│     │  ├─ ShortLinkController.java
│     │  └─ UrlTitleController.java
│     └─ remote/dto
│        └─ ShortLinkRemoteService.java
│
└─ project
   └─ src/main
      ├─ java/com/nageoffer/shortlink/project
      │  ├─ controller
      │  │  ├─ ShortLinkController.java
      │  │  ├─ ShortLinkNotFoundController.java
      │  │  └─ UrlTitleController.java
      │  ├─ service
      │  │  ├─ ShortLinkService.java
      │  │  ├─ UrlTitleService.java
      │  │  └─ impl
      │  │     ├─ ShortLinkServiceImpl.java
      │  │     └─ UrlTitleServiceImpl.java
      │  ├─ dto
      │  │  ├─ req
      │  │  └─ resp
      │  ├─ dao
      │  │  ├─ entity
      │  │  └─ mapper
      │  ├─ toolkit
      │  │  ├─ HashUtil.java
      │  │  └─ LinkUtil.java
      │  ├─ config
      │  │  └─ RBloomFilterConfiguration.java
      │  └─ common
      │     ├─ constant
      │     └─ enums
      └─ resources
         ├─ application.yaml
         ├─ shardingsphere-config-dev.yaml
         ├─ shardingsphere-config-prod.yaml
         └─ templates/notfound.html
```

各部分的职责可以简单记为：

```text
admin Controller       后台接口入口
ShortLinkRemoteService 后台访问中台的手写 HTTP 客户端
project Controller     中台短链接口和跳转入口
ServiceImpl            创建、查询、修改和跳转的核心业务
DTO                    定义接口请求和响应数据
DO                     映射短链接数据库记录
Mapper                 访问 t_link 和 t_link_goto
Toolkit                生成短链后缀、计算缓存有效时间
Config                 初始化布隆过滤器等基础组件
Resources              保存应用、分片和兜底页面配置
```

## 2. admin 与 project 的调用关系

`admin` 中的 `ShortLinkRemoteService` 使用 Hutool `HttpUtil` 请求 `project`：

```text
前端 / Apifox
    ↓
admin ShortLinkController（8002）
    ↓ 调用本地 Java 方法
ShortLinkRemoteService
    ↓ HttpUtil 发送 HTTP 请求
project ShortLinkController（8001）
    ↓
ShortLinkServiceImpl
    ↓
MySQL / Redis
```

例如后台调用：

```java
shortLinkRemoteService.createShortLink(requestParam);
```

实际会发送：

```http
POST http://127.0.0.1:8001/api/shortlink/v1/create
```

因此，`ShortLinkRemoteService` 不是把中台代码复制到后台执行，而是中台功能在后台的本地代理。当前实现是手写 HTTP 客户端，后续可以改为 OpenFeign 和服务发现。

## 3. 三个 Controller

### 3.1 ShortLinkController

`project` 中的短链接控制器提供：

```text
POST /api/shortlink/v1/create  创建短链接
POST /api/shortlink/v1/update  修改短链接
GET  /api/shortlink/v1/page    分页查询短链接
GET  /api/shortlink/v1/count   查询各分组短链接数量
GET  /{short-uri}              访问短链接并重定向
```

Controller 负责接收参数、调用 Service 和包装响应，真正的业务位于 `ShortLinkServiceImpl`。

### 3.2 ShortLinkNotFoundController

短链接不存在或已经过期时，跳转业务执行：

```java
response.sendRedirect("/page/notfound");
```

浏览器收到重定向响应后重新请求 `/page/notfound`，Spring 再调用：

```java
@RequestMapping("/page/notfound")
public String notfound() {
    return "notfound";
}
```

根据 MVC 视图配置，最终渲染：

```text
resources/templates/notfound.html
```

所以 `restoreUrl()` 不是直接调用 `notfound()` 方法，而是让浏览器重新发起请求，再由 Spring 完成路由和页面渲染。

### 3.3 UrlTitleController

标题接口根据 URL 请求目标网站，并使用 Jsoup 读取 HTML 的 `<title>`：

```java
Document document = Jsoup.connect(url).get();
return document.title();
```

调用示例：

```http
GET /api/shortlink/v1/title?url=https://www.example.com
```

该功能已经可以独立调用，但当前没有接入创建短链接的业务流程。以后可以由前端在用户输入原始链接后调用，用返回的标题自动填充描述。

## 4. DTO：短链接请求和响应对象

### 4.1 请求 DTO

```text
ShortLinkCreateReqDTO 创建短链接时提交的参数
ShortLinkPageReqDTO   分页查询条件
ShortLinkUpdateReqDTO 修改短链接时提交的参数
```

`ShortLinkPageReqDTO` 主要包含：

```text
gid      查询哪个分组
current  查询第几页
size     每页查询多少条
```

### 4.2 响应 DTO

```text
ShortLinkCreateRespDTO          创建成功后返回 gid、原始链接和完整短链接
ShortLinkGroupCountQueryRespDTO 返回一个 gid 下的短链接数量
ShortLinkPageRespDTO            规定分页结果中一条短链接记录的格式
```

分页接口返回：

```java
Result<IPage<ShortLinkPageRespDTO>>
```

结构可以理解为：

```text
Result
└─ IPage
   ├─ current 当前页
   ├─ size    每页数量
   ├─ total   总记录数
   ├─ pages   总页数
   └─ records
      ├─ ShortLinkPageRespDTO 第一行
      ├─ ShortLinkPageRespDTO 第二行
      └─ ShortLinkPageRespDTO 第三行
```

简单记忆：

```text
PageReqDTO  决定怎么查这一页
PageRespDTO 决定页面中每一条记录返回什么
IPage       包装当前页记录和分页统计信息
```

## 5. DAO：两张短链接逻辑表

### 5.1 ShortLinkDO 与 t_link

`ShortLinkDO` 对应逻辑表 `t_link`，保存完整业务数据：

```text
domain          短链域名
shortUri        短链后缀
fullShortUrl    完整短链接
originUrl       原始链接
gid             分组标识
enableStatus    启用状态
validDateType   有效期类型
validDate       过期时间
describe        描述
favicon         网站图标
clickNum        点击次数
```

`t_link` 按 `gid` 分为 16 张物理表：

```text
t_link_0 ... t_link_15
```

`gid` 的主要作用是帮助 ShardingSphere 定位物理分表。同一 `gid` 下可以有多条短链接，所以只用 `gid` 不能唯一确定一条记录。

### 5.2 ShortLinkGotoDO 与 t_link_goto

`ShortLinkGotoDO` 对应逻辑路由表 `t_link_goto`，主要保存：

```text
fullShortUrl → gid
```

用户访问短链接时只有 `fullShortUrl`，并不知道 `gid`。而 `t_link` 又以 `gid` 作为分片键，所以系统需要先查询路由表得到 `gid`。

完整数据库查询过程：

```text
fullShortUrl
    ↓ 查询 t_link_goto
得到 gid
    ↓ gid 定位 t_link 物理分表
gid + fullShortUrl
    ↓ 定位具体短链接记录
得到 originUrl
    ↓
302 重定向
```

两个条件的职责是：

```text
gid          决定去哪张 t_link 分表查询
fullShortUrl 决定在该分表中查询哪一条记录
```

`t_link_goto` 自身也分为 16 张表，但使用 `full_short_url` 作为分片键：

```text
fullShortUrl → t_link_goto_x → gid → t_link_x → originUrl
```

## 6. ShortLinkServiceImpl：核心业务

核心方法包括：

```text
createShortLink()             创建短链接并预热缓存
pageShortLink()               分页查询指定分组的短链接
listGroupShortLinkCount()     统计各 gid 下的短链接数量
updateShortLink()             修改短链接，处理跨分组迁移
restoreUrl()                  查询原始链接并重定向
generateSuffix()              生成短链接后缀
getFavicon()                  获取目标网站图标
```

### 6.1 创建短链接与缓存预热

创建流程：

```text
原始链接 + 当前时间
    ↓ MurmurHash32 + Base62
生成短链后缀
    ↓
拼接 fullShortUrl
    ↓
构造 ShortLinkDO 和 ShortLinkGotoDO
    ↓ 事务写入
t_link + t_link_goto
    ↓
写入 Redis 正向缓存
    ↓
加入布隆过滤器
    ↓
返回创建结果
```

缓存预热指的是：短链接刚创建成功，就提前把映射写入 Redis：

```text
fullShortUrl → originUrl
```

这样第一次访问短链接时就可以直接命中缓存，不必先查询数据库。

布隆过滤器用于生成阶段的初步去重，数据库唯一键仍应作为并发和哈希冲突下的最终保障。

### 6.2 分页查询

`pageShortLink()` 的主要条件：

```text
gid = 指定分组
enable_status = 0
del_flag = 0
按 create_time 倒序
```

查询结果先得到 `IPage<ShortLinkDO>`，然后将每一条 DO 转换为 `ShortLinkPageRespDTO`。

### 6.3 分组数量统计

`listGroupShortLinkCount()` 按 `gid` 分组并执行 `count(*)`：

```sql
SELECT gid, COUNT(*) AS shortLinkCount
FROM t_link
WHERE gid IN (...)
  AND enable_status = 0
GROUP BY gid;
```

返回结果可用于后台分组列表：

```text
默认分组（12）
学习资料（8）
技术文章（5）
```

### 6.4 修改短链接

修改时要区分原分组和目标分组：

```text
originGid 原来的分组
gid       修改后的分组
```

查询旧记录时必须使用：

```text
originGid + fullShortUrl
```

如果没有 `originGid`，跨分组修改时就无法定位记录原来所在的物理分表。

同组修改：

```text
originGid == gid
→ 直接更新原 t_link 分表中的记录
```

跨组修改：

```text
originGid != gid
→ 删除旧 gid 分片中的记录
→ 插入新 gid 分片
→ 更新 t_link_goto 中的 gid
```

因为 `gid` 是分片键，修改 `gid` 本质上是把记录从一张物理表迁移到另一张物理表。

当前代码修改短链接后没有同步删除或更新 Redis 正向缓存。如果修改 `originUrl` 或有效期，缓存过期前可能继续使用旧数据，后续应补充缓存一致性处理。

## 7. restoreUrl：短链接重定向核心逻辑

### 7.1 Redis 中保存什么

Redis 正向缓存保存：

```text
Key:   short-link_goto_{fullShortUrl}
Value: originUrl
TTL:   根据短链接有效期计算
```

例如：

```text
short-link_goto_nurl.ink/aB3x92
→ https://www.example.com/article
```

正向缓存命中后，可以直接取得原始链接并完成重定向，不需要查询两张数据库表。

### 7.2 缓存穿透与缓存击穿

缓存穿透指：

> 请求的数据本来就不存在，Redis 和数据库都查不到，但大量请求仍不断穿过 Redis 访问数据库。

当前解决方式：

```text
布隆过滤器 + Redis 空值缓存
```

缓存击穿指：

> 某条真实存在的热点短链接缓存突然过期，大量并发请求同时访问数据库。

当前解决方式：

```text
Redisson 分布式锁 + 锁内二次检查 Redis
```

两者的区别：

```text
缓存穿透：查询根本不存在的数据
缓存击穿：热点数据存在，但缓存刚好失效
```

### 7.3 布隆过滤器的判断特点

布隆过滤器使用多个哈希函数把数据映射到位数组。不同数据可能映射到已经被其他数据占用的位置，因此存在误判：

```text
判断不存在 → 一定不存在
判断存在   → 可能存在，也可能不存在
```

参数设置合理时误判概率较低，但不能因为它判断“存在”就直接认定数据库中一定有记录。

### 7.4 Redis 空值缓存

空值缓存不是 MySQL 表，也不是真正保存 Java 的 `null`。当前代码在 Redis 中保存占位符 `-`：

```text
Key:   short-link_is-null_goto_{fullShortUrl}
Value: -
TTL:   30 分钟
```

它表达的是：

> 这条短链接最近已经查询过数据库，确认不存在或已经过期，暂时不要再次访问数据库。

空值缓存属于以少量 Redis 空间换取数据库保护和响应速度的策略。它还可以处理布隆过滤器误判、短链删除以及短链过期等情况。

### 7.5 完整执行顺序

`restoreUrl()` 的准确顺序是：

```text
1. 拼接完整短链接 fullShortUrl

2. 查询 Redis 正向缓存
   ├─ 命中：得到 originUrl，直接 302 跳转
   └─ 未命中：继续

3. 查询布隆过滤器
   ├─ 判断不存在：直接跳转 notfound
   └─ 判断可能存在：继续

4. 查询 Redis 空值缓存
   ├─ 命中：之前已确认不存在或过期，跳转 notfound
   └─ 未命中：继续

5. 获取 fullShortUrl 对应的 Redisson 分布式锁

6. 获得锁后再次查询 Redis 正向缓存
   ├─ 命中：其他线程已经完成回填，直接跳转
   └─ 未命中：当前线程负责查询数据库

7. 使用 fullShortUrl 查询 t_link_goto
   ├─ 不存在：写入 30 分钟空值缓存，跳转 notfound
   └─ 存在：得到 gid

8. 使用 gid + fullShortUrl 查询 t_link
   ├─ gid 定位物理分表
   └─ fullShortUrl 定位具体记录

9. 检查删除状态、启用状态和有效期
   ├─ 无效或过期：写入空值缓存，跳转 notfound
   └─ 正常：得到 originUrl

10. 将 fullShortUrl → originUrl 回填到 Redis 正向缓存

11. 302 重定向到 originUrl

12. finally 中释放分布式锁
```

流程图：

```text
用户访问 /{short-uri}
        ↓
拼接 fullShortUrl
        ↓
Redis 正向缓存
   ├─ 命中 ─────────────────────────→ 302 跳转
   └─ 未命中
        ↓
布隆过滤器
   ├─ 一定不存在 ───────────────────→ notfound
   └─ 可能存在
        ↓
Redis 空值缓存
   ├─ 命中 ─────────────────────────→ notfound
   └─ 未命中
        ↓
获取分布式锁
        ↓
再次查询 Redis 正向缓存
   ├─ 命中 ─────────────────────────→ 302 跳转
   └─ 未命中
        ↓
fullShortUrl 查询 t_link_goto
   ├─ 不存在 → 写空值缓存 ──────────→ notfound
   └─ 得到 gid
        ↓
gid + fullShortUrl 查询 t_link
   ├─ 不存在/无效/过期
   │      → 写空值缓存 ─────────────→ notfound
   └─ 正常
        ↓
回填 Redis 正向缓存
        ↓
302 跳转 originUrl
        ↓
释放分布式锁
```

### 7.6 为什么锁内还要再查 Redis

假设同一条热点短链同时收到三个请求：

```text
A、B、C 第一次查 Redis 都没有命中
A 获得锁
B、C 等待锁
A 查询数据库并回填 Redis，然后释放锁
B 获得锁后再次查询 Redis，此时已经命中
C 获得锁后再次查询 Redis，此时也已经命中
```

最终只有 A 访问数据库，B 和 C 使用 A 回填的数据。这一步叫双重检查，是防止缓存击穿的关键。

分布式锁按照 `fullShortUrl` 区分，不同短链接使用不同的锁，因此不会把所有短链接请求全部串行化。

## 8. 两个 Toolkit 工具类

### 8.1 HashUtil

`HashUtil` 负责生成短链接后缀：

```text
原始链接 + 当前时间
    ↓ MurmurHash32
得到整数哈希值
    ↓ Base62
得到短链后缀
```

例如：

```text
https://example.com/article + 时间戳
→ aB3x92
→ nurl.ink/aB3x92
```

加入当前时间可以让同一个原始链接在不同时刻创建时得到不同后缀。哈希算法本身不能绝对保证不重复，所以还需要布隆过滤器初步判断和数据库唯一键最终兜底。

### 8.2 LinkUtil

`LinkUtil` 不是直接判断短链接是否过期，而是计算 Redis 正向缓存应该保存多长时间：

```text
validDate == null
→ 使用永久短链的默认缓存时间

validDate != null
→ validDate - 当前时间
→ 得到 Redis TTL
```

真正判断短链接当前是否过期的是 `restoreUrl()`：

```java
shortLinkDO.getValidDate().isBefore(LocalDateTime.now())
```

二者区别：

```text
LinkUtil   计算缓存还能保存多久
restoreUrl 判断短链接现在是否已经过期
```

## 9. Favicon 和标题

`getFavicon()` 用于请求目标网站并读取图标地址，创建短链接时将结果写入 `ShortLinkDO.favicon`。

`UrlTitleServiceImpl` 使用 Jsoup 读取目标页面标题。两者都是向外部网站发起网络请求，可能受到目标站点超时、拒绝访问、重定向和 HTML 格式影响。

当前 `getFavicon()` 在创建短链接事务内同步执行，而且返回值包含说明文字，不是纯图标 URL。后续可以考虑：

- 设置连接和读取超时。
- 只保存绝对图标 URL。
- 抓取失败时返回默认图标。
- 将标题和图标抓取改为异步任务，避免延长创建事务。

## 11. 当前代码值得注意的问题

### 11.1 修改后的缓存一致性

修改 `originUrl`、有效期或状态后，应删除或更新对应的 Redis 正向缓存，否则可能继续跳转到旧地址或沿用旧 TTL。

### 11.2 布隆过滤器恢复

布隆过滤器只在创建短链接时加入新数据。如果 Redis 数据丢失或布隆过滤器重新初始化，数据库已有短链接可能被判断为不存在，需要设计启动重建或恢复机制。

### 11.3 锁的使用

当前使用 `lock.lock()`，如果持锁进程异常退出，需要依赖 Redisson 看门狗续期和释放机制。实际项目还可以考虑 `tryLock()`、等待时间以及失败后的降级处理。

### 11.4 主表查询不到时的兜底

当前代码在路由表存在、但 `t_link` 主记录查询不到时，没有明确写空值缓存和跳转 `notfound`。应补充兜底，避免请求没有正常响应。

### 11.5 远程调用地址硬编码

`admin` 当前直接请求 `127.0.0.1:8001`，只适合本地学习环境。后续可以使用 OpenFeign、配置中心和服务发现替代固定地址。

### 11.6 数据库脚本

## 12. 核心记忆总结

### 12.1 创建短链接

```text
生成短链后缀
→ 写 t_link
→ 写 t_link_goto
→ 预热 Redis 正向缓存
→ 加入布隆过滤器
```

### 12.2 数据库两级路由

```text
fullShortUrl
→ t_link_goto
→ gid
→ 定位 t_link 分表
→ gid + fullShortUrl 定位记录
→ originUrl
```

### 12.3 跳转保护

```text
Redis 正向缓存：快速跳转
布隆过滤器：拦截确定不存在的请求
Redis 空值缓存：缓存数据库已确认的不存在状态
分布式锁：防止热点缓存失效时大量请求同时查询数据库
双重检查：让等待锁的线程使用已经回填的缓存
t_link_goto：根据完整短链取得 gid
t_link：取得原始链接和有效期等完整信息
```

最简完整链路：

```text
访问短链接
→ Redis
→ 布隆过滤器
→ 空值缓存
→ 分布式锁
→ 再查 Redis
→ t_link_goto
→ t_link
→ 回填 Redis
→ 302 重定向
```
